# `ref_tilt` for bends: implementation record (2026-08-02)

Octopus could misalign a bend but could not express a **vertical** one. A single
`tilt` keyword conflated two different things, and the codes do not agree on
which one the word names:

| meaning | Bmad | MAD-X | Octopus (before) | Octopus (now) |
|---|---|---|---|---|
| roll the magnet **body**; design orbit unchanged — an *error* | `roll` | `EALIGN, dpsi` | `tilt` | `tilt` |
| roll the **design orbit plane**; the reference trajectory bends elsewhere — a *design choice* | `ref_tilt` | `sbend, tilt=` | missing | `ref_tilt` |

So MAD-X's `tilt` **on a bend** is Bmad's `ref_tilt`. Translating a MAD-X lattice
by matching the keyword spelling gives a rolled magnet where the lattice meant a
rolled orbit — a machine error where the design intended geometry.

## What was built

`src/elements/ref_tilt.jl`: a `RefTilted` wrapper applied in `compile_runtime`
outside `_misalignment_wrap`. The map is a conjugation — rotate $(x,p_x)$
against $(y,p_y)$ by $-\psi$, track, rotate back. A roll about $s$ maps the
$s=0$ plane to itself, so there is no drift onto a displaced face and no
path-length term, and `z`/`pz` pass through untouched. The rotation is taken
from `_misalign_matrix` rather than composed locally, for the same reason the
patch does it: that routine's sign and composition order are pinned against PTC,
and a second copy would be free to drift away from it.

Declared on `:sbend` only, but the wrap is applied wherever the parameter is
set, so it is never silently dropped. On a straight element it coincides with
`tilt` bit for bit, which is one of the tests.

## The tracking-completeness question, settled

The scoping entry in `docs/todo.md` had already corrected itself once on this:
an earlier draft said the downstream geometric consequence "needs the survey
Octopus does not have". That is true for **reporting** where a magnet sits in
space and false for **tracking**. The lattice is a sequence of maps in local
curvilinear frames; a bend already turns its frame by $hL$, and conjugating it
with an $s$-roll makes it turn in a rolled plane, after which the next element
receives coordinates in the new frame. Nothing absolute is required. The
correction held up — the implementation is complete for tracking, and a survey
is still needed only to answer where the magnet is in the building.

## What the comparison overturned

The same entry predicted the ordering: *"`ref_tilt` is design geometry, so it
composes **outside** the misalignment frames, not inside them."* Measured
against PTC, that is true of the maps and does not settle the question it was
invoked to settle.

Both codes displace the same magnet — the rolled one. They differ over **which
axes the alignment error is measured along**:

| | frame the offset and pitches live in | source |
|---|---|---|
| Bmad | the **rolled** frame | `track_a_bend` rotates by `ref_tilt`, then calls `offset_particle` inside it |
| MAD-X | the **unrolled** design frame | `EALIGN` is survey data about the machine, so `dx` stays horizontal |

`ref_tilt` stays the outer map in both; the `:madx` branch conjugates the rigid
transform into the rolled frame, $W \mapsto R_z(-\psi) W R_z(\psi)$ and
$d \mapsto R_z(-\psi) d$. The split therefore rides on the existing
`misalign_convention`, alongside the reference point and the rotation
composition order — a third face of the same convention, not a new switch.

Deviations from PTC at `ref_tilt = 0.3` on a combined-function bend:

| model | `dx` only | all six |
|---|---|---|
| error quoted in the rolled frame (the prediction) | 2.0e-4 | 3.5e-4 |
| offset rotated, $W$ left alone | — | 1.2e-4 |
| error quoted in the unrolled frame (`:madx`) | **2.8e-13** | **4.5e-13** |

Both parts of the transform have to move together; rotating only the offset
leaves a residual larger than the effect being chased.

How it was found, since the method generalises: neither pure composition order
matched (2.0e-4 one way, 8.8e-6 the other — the second smaller, and misleadingly
so). Scanning the offset *direction* through a free angle $\alpha$ and watching
the deviation collapse to 2.8e-13 at exactly $\alpha = -\psi$ identified the
frame directly, rather than by reasoning about PTC internals that were not to
hand. The all-six case then separated "offset only" from "offset and rotation".

**The prediction that a two-parameter case would be needed was exactly right.**
Every model in that table agrees when only one of the two parameters is nonzero.
None of the one-at-a-time cases that pin the rest of the misalignment work could
have caught this, and neither could a symplecticity test — every candidate is a
conjugation of a symplectic map and so is symplectic whichever frame is wrong.

## Reference cases

Five added to `validation/generate_ptc_reference.jl`, driven through
`sbend, tilt=`, `MAD-X 5.03.06`, `model=1, exact=true, time=false`:

| case | what it pins | deviation |
|---|---|---|
| `sbend_reftilt` | the map and the keyword meaning | 3.5e-13 |
| `sbend_reftilt_vertical` | $\psi = \pi/2$, the case that was inexpressible | 4.1e-13 |
| `cfbend_reftilt` | the rolled curved-frame multipole kick | 4.6e-13 |
| `cfbend_reftilt_mis_dx` | the frame the error is quoted in | 2.8e-13 |
| `cfbend_reftilt_mis_all` | the same, with all six degrees of freedom | 4.5e-13 |

The full contract is 46 cases, worst deviation 5.0e-13. Regenerating the table
added 25 rows and changed no existing byte.

## Not done

- **Bmad's branch is unvalidated.** `:bmad` is read from `track_a_bend` and has
  no reference case, because there is no Bmad in this repository's validation
  path. It is the default, and it is in exactly the position the `:bmad`
  rotation-composition order was already in — asserted from source, not
  measured. A Bmad comparison would close both at once.
- **Survey/reporting.** `ref_tilt` still cannot say where a magnet is in space.
  That is the geometry layer of the theory note's Section 8 and is unchanged.
- **`RBendSpec`** inherits `ref_tilt` through `:sbend` and is untested with it.
