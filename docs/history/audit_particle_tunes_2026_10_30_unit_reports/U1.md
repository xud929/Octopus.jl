## Scope and provenance

The declared hypothesis was that a persistent particle label can be lost or
misbound at compilation, continuation, coordinate reset, MPI agreement, or a
refused execution window. The reviewer also checked whether the public bare
tracking guard could bypass ownership and whether an ordinary line acquired
per-turn work.

## Leads and reproductions

### LEAD U1-1 [Major, confidence high] src/tasks/ParticleTunes.jl:62

Claim: the initial implementation could enter incompatible MPI collective
sequences when only some ranks had a particle-tune placement.

Mechanism: `_prepare_particle_tunes!` originally executed the local early
return `!present && state === nothing && return nothing` before any agreement
on whether to enter preparation. A rank with ordinary `Linear6D` bypassed
the collective error verdict entered by a rank with active particle tunes.
The later layout checks could not protect a rank that had already returned.

Repro: launch `U1_mpi_mismatch.jl presence RECEIPT_DIR` in package
mode with the repository's MPI environment and exactly four ranks, under a
timeout. The script writes one receipt per rank before entry and requires
all four to refuse with unchanged coordinates. The old branch is expected
to hang or misalign collectives; that expectation is not an executed result
from U1.

Root response: accepted; global presence/state agreement now precedes the
local early return, only when MPI has more than one rank. U1 reread the fix.
The injected-old-admission four-rank negative control did reproduce collective
misalignment, rather than the launcher's initially predicted timeout:
`result/particle_tunes_mpi_red_presence/u1_presence_rank_0.txt` contains only
the entry marker, while rank 1 records `refused=true unchanged=false` and a
spurious shard-count error for `[0, 2, 2, 2]` (six particles, despite the
seven-particle input). Ordinary ranks had already changed coordinates before
the mismatched collective produced that refusal. U1 read these receipts;
the launcher expectation was corrected to accept the actual stated failure
mechanism. The fixed real-MPI run passed at **1, 2 and 4 ranks** in
`result/particle_tunes_mpi_fixed.log`; each multi-rank receipt records eight
schema refusals, and every rank records six exact-source cases, collective
source-failure coverage and empty shards. U1 read the launcher summary and
four-rank rank-0 receipt. The portable archived negative-control launcher
also executed against these sources. In that run all four ranks wrote entry
markers and MPI aborted before any completion marker, with `Fatal error in
internal_Allgather: Message truncated` (rank 0 received incompatible message
sizes). The first corrected predicate was still too narrow: it demanded a
peer's completion receipt with changed coordinates and did not admit an
earlier MPI-level abort. Both runs demonstrate collective misalignment; the
specific truncation signature plus all four entry markers must count as the
same negative-control mechanism. Source fixes did not change in response to
either launcher-expectation correction.

The final corrected portable launcher completed successfully (exit 0), as
recorded in `result/particle_tunes_mpi_portable_final.log`. Both `planes` and
`presence` controls reported `timedout=false receipts=4 expected_defect=true`.
The presence mechanism was `peers_changed=false corrupted_counts=false
truncated_allgather=true timedout=false`: the precise MPI truncation occurred
before a peer wrote its completion receipt. U1 read this final receipt;
the fixed 1/2/4-rank execution and both pre-fix collective failure mechanisms
are now covered by executed controls.

### LEAD U1-5 [Moderate, confidence high] src/tasks/Tasks.jl:1035

Claim: the promised refusal of simultaneous execution of the same particle-
tune task is not enforced by the initial manager's ordinary Boolean.

Mechanism: both public `execute!` calls may observe `running=false`, enter
compilation and preparation, and pass the second check in
`_prepare_particle_tunes!` before either sets the flag. The flag is first
set after both preparation stages. Existing recursion tests enter from a
callback or observer after this point, and therefore do not cover concurrent
admission. The PhaseSpaceReset sibling has the same shape. U1 found no public
contract declaring shared-task concurrent execution outside the API promise.

Repro: [`U1_concurrent_admission.jl`](U1_concurrent_admission.jl) wraps a CPU vector with
an `axes()` barrier. After one successful binding, two spawned `execute!`
calls are held inside the storage-signature computation, past the manager's
Boolean check but before it can set the flag. The driver releases after
arrivals plus completed refusals total two, with a 10-second deadline and a
second 10-second worker-completion bound. Thus the fixed version can reject
one caller before the barrier without deadlocking the witness. It requires
one success and one concurrent/recursive-execution refusal. U1 did not run
Julia; the witness was supplied to root before any repair.

The first executed fixture used an immutable custom vector wrapper and both
workers instead failed the existing WeakRef ownership check. That execution
showed two arrivals but is not counted as defect reproduction. The wrapper
was changed to a mutable object before the admission witness was rerun; this
preserves the actual array object's identity across the existing checks.

Root response: accepted; a task-owned atomic admission guard at the public
entry now covers initialized and first-time tasks before cache/loss mutation.
U1 reread the patch: failed CAS acquisition throws outside `try/finally`, so
the rejected caller cannot release its peer's guard; accepted execution and
both mutating clear APIs release in `finally`, including preflight failures.
The Beam overload forwards exactly once to the guarded representation entry,
and distinct task instances hold distinct atomics. The explicit clears use
the same guard because testing only the later manager Boolean would still
permit a clear during preparation. The corrected mutable-vector negative
control in `result/particle_tunes_concurrent_admission_red2.log` printed
`U1-CONCURRENT-ADMISSION arrived=2 accepted=2 refused=0`; both calls completed
successfully and the required one-success assertion failed `2 == 1`.
The positive control executed in
`result/particle_tunes_concurrency_and_views.log`:
`U1-CONCURRENT-ADMISSION arrived=1 accepted=1 refused=1`; the rejected result
names concurrent/recursive execution. The ordinary-path numerical and
allocation checks subsequently passed as recorded below.
The permanent atomic-admission testset initially passed **6/6** in
`result/particle_tunes_targeted_final.log`; its expanded concurrent-clear
coverage passed **11/11** in `result/particle_tunes_atomic_and_mpi_controls.log`
before that process entered the separate negative MPI experiment.

### LEAD U1-6 [Moderate, confidence high] src/tasks/Tasks.jl:47

Claim: weak ownership of immutable coordinate-array wrappers loses a live
ensemble's identity across garbage collection. This affects particle tunes,
the PhaseSpaceReset sibling, and the shared ordinary/strong-strong loss-record
owner discriminator.

Mechanism: a WeakRef to an immutable wrapper can reference a temporary box
that no other object retains, although the beam retains the wrapper's parent
storage. The first failed concurrency fixture exposed this with a custom
immutable AbstractVector; the independent validation agent then reproduced
it with standard `SubArray` coordinate views and an explicit `GC.gc()`.
This follow-up is a real supported-storage defect, distinct from the original
concurrency fixture's invalid refusal.

Measured negative controls, read directly by U1:

- `result/particle_tunes_concurrency_and_views.log`: both particle-tune and
  reset tasks passed the first execution on views, then refused the same
  representation after GC with the respective coordinate-ownership error.
- `result/particle_tunes_view_loss_red.log`: ordinary TrackingTask and the
  StrongStrongTask shared binding both reported `owner_survived=false
  record_preserved=false old_counts=Int32[1] current_counts=Int32[0]`.
  TrackingTask also reported an unattributed loss: a previously logged loss
  had become detached from its original record.

Root response: accepted and repaired through one shared
`_coordinate_storage_owner` helper. Mutable arrays retain WeakRef ownership;
immutable wrappers use `_RetainedCoordinateOwner`, deliberately retaining
the wrapper and its parents until that owner binding is cleared or replaced.
Both expose `.value`, preserving the identity checks. U1 re-walked all source
call sites: both task constructors, the shared loss allocator and both
strong-strong references accept either owner form; all six reset and tune
owners use the same helper; clear/replacement paths release their respective
bindings. No stale WeakRef-only allocator signature or owner-capture site
remains. The cost is bounded lifetime retention for immutable wrappers,
not retention of ordinary mutable vectors. In
`result/particle_tunes_views_and_reentrant.log`, the corrected immutable-view
testset passed **16/16** across tunes, reset, ordinary loss and the shared
strong-strong binding; the pre-existing reset refusal/reentrancy neighbour
passed **40/40**. U1 read both summaries.

The first integrated run of this new view test had an incorrect fixture
expectation that reset `completed_trials` accumulated across execute windows.
The implementation correctly returned one trial for each one-turn window
(`1 == 2` failed). U1 found the expectation by source review; the validation
agent changed the test to assert one completed trial and the preserved
reference epoch/capture turn, then ran the corrected 16-check testset above.
That fixture failure is not evidence of an additional source defect.

## Source checks that were sound

- CPU and CUDA public context-aware `track!` entries both retain the
  task-only guard. The private `_track_admitted!` boundary is called after the
  owning task's binding admission; bound objects cannot be passed to another
  public task or bare tracking entry to bypass owner checks.
- Ownership compares all six coordinate-array identities through storage owners,
  lengths/axes, precision, backend/device, global count and shard interval.
  An immutable `Phase6DRep` box is not mistaken for the arrays' owner.
- The initializer is reached at its explicit plan segment after upstream
  tracking, and later placements see earlier initialized maps. Device streams
  are synchronized before any first-passage coordinate read.
- Coordinate-independent sources avoid coordinate host copies. Callback
  sources stage host coordinates once and collectively reject non-finite
  entrances before invoking any callback. Staged arrays and runtime are
  installed only after the success verdict.
- The task owns binding storage outside runtime and plan caches. Recompilation
  refreshes transforms while reusing tune/rotation arrays. Reset operations
  keep independent state and are detected with their own predicate, so the
  generic task-only trait does not mistake a tune map for a reset.
- Public tune-table queries return independent copies; clear refuses during
  execution, advances only the tune preparation epoch, and empties plans
  without modifying coordinates, the reset reference or turn cursor.
- The ordinary no-feature CPU early return is guarded by an unrolled runtime
  entry walk. The final once-per-execute allocation/walk testset passed
  37 checks, and the Core.Box tripwire passed five; detailed receipts follow.
- StrongStrongTask refuses active tune runtimes in its line-splitting stage;
  the new variant is not silently tracked without persistent ownership.
