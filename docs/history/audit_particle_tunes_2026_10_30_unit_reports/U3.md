# U3: independent particle-tune validation and neighbour checks

## Scope and provenance

This unit reviewed the proposed `Linear6DSpec` runtime variant independently of
the implementation author, implemented independent numerical/source/lifecycle
checks, and executed the source-audit witnesses supplied by U1. It is a targeted
feature review, not a repository-wide audit. Work started at
`529d8e9ddea111ad4c1b95d7d1b43132d3d452ad`; measured execution used Julia 1.12.4,
four Julia threads and the available NVIDIA RTX 4500 Ada. Actual CPU worker and
CUDA launch receipts, rather than requested policy objects alone, are checked.
The parent campaign report owns the final tree, gate and push receipts.

Read surfaces: the old `linear6d.jl` optics construction and matrix convention;
the new source parser, RNG adapter, normalizer, initialization and indexed
kernel in `particle_tunes.jl`; particle-binding admission, persistence and clear
paths; reset ownership and loss-record siblings; CPU/CUDA admitted tracking
paths; the MPI extension and existing seam harness; runtime-variant reflection
and precision census consumers. The source author owns U1's independent
lifecycle audit, while U2 owns metadata/contract source audit. This unit did not
review unrelated strong-strong solver internals or all package source files.

The dense map bound is `128 eps(T) turns` times each coordinate's reference
scale. The response convolution uses the forward carrier
`|w(0)| + sum |kappa|` for each plane with the same multiplier. This avoids an
artificial unit-sized absolute floor. Independent action, phase, centroid and
covariance checks constrain the response separately.

Executed standalone validation used `N=17`, 24 response turns, both precisions
and five policies: 50 cases passed, with maximum dense normalized error ratio
`0.011829078612328323`. Dense maximum absolute errors were
`3.469446951953614e-18` (Float64) and `1.7503769440818662e-9` (Float32).
The largest response normalized ratio was `0.006722037755137576`; Float32
maximum relative action drift was `1.7685815243417835e-6`, maximum phase gap
`2.3888387946362613e-6`, centroid gap `6.500587524218074e-9` and covariance gap
`6.03796585915822e-12`. The mandatory backend driver ran all 36 element
instances at N=2000, turns=2, including the new runtime; all its CPU/CPU and
CPU/CUDA declared rounding classes passed. The new runtime's six coordinates
were bitwise equal under its declared class.

## Confirmed findings and executed controls

**U3-1, RNG primitive adapter.** The first focused run passed 103 dense/map
checks and 172 input/entrance checks, then the public custom distribution
protocol failed after seven distribution checks with
`MethodError: no method matching rand_generic(::_ParticleTuneRNG, ::Type{UInt32})`.
`PTProbeAdapterDraws` (`test/particle_tunes_probe.jl:259`) exposed the error
through `rand(rng, distribution)`, not an internal RNG construction. The core
author supplied explicit primitive integer methods. The retained fixture now
exercises Bool, signed and unsigned 8/16/32/64/128-bit draws, corresponding bulk
arrays, Float32, range integers, `randn` and bulk Float64. The corrected source
and all distribution checks passed.

**U1 admission/loss failure, reproduced here.** Clearing and disabling particle
tunes left an empty manager. On a later ordinary-path failure, cleanup restored
an old beam's loss owner even though the new beam had already tracked and lost
a particle. RED: old record/owner restored `true/true`, dead particle present,
count `[0]`. GREEN after admission-counter correction: old record/owner
restored `false/false`, count `[1]`. The permanent test is "Particle tunes:
clearing and disabling preserves an admitted failed run". Its injected later
particle failure checks the real public execution boundary.

**U1 MPI admission/schema seam, reproduced here.** A child-local replacement
restored the old early-return/no-schema-agreement implementation without
changing repository source. With four ranks using different named planes, all
four incorrectly accepted and changed coordinates. With feature presence only
on rank zero, rank zero never completed; peers advanced coordinates and then
reported inconsistent shard counts `[0,2,2,2]` (global six despite input seven),
and MPI aborted a mismatched `MPI_Allgather` with a message truncation error.
This is a collective-sequence defect, not a numerical tolerance issue. The
fixed harness additionally rejects mismatches in presence, planes, stream,
omitted nominal tune, seed, RNG method, endpoint optics and runtime precision;
it checks unchanged coordinates and unbound tables. The fixed one-, two- and four-rank launchers all passed. All seven rank
receipts recorded six direct/sampled cases; the six ranks in multiprocess
launches each additionally recorded eight coherent mismatch refusals. Both
precisions, uneven/empty shards, one-rank source failure/retry and collective
finite-entrance validation executed. The intentional undivided references on
each launched rank emitted the existing single-process-policy warning; they
are explicit reference calculations, not unintended duplicated sharded work.

**U1 simultaneous admission race, reproduced here.** A bounded custom vector
`axes()` barrier forced both public calls beyond the old Bool check. Corrected
RED fixture: arrivals=2, accepted=2, refused=0. GREEN with task-entry atomic
CAS: arrivals=1, accepted=1, refused=1; the refusal names concurrent/recursive
execution. The permanent fixture at `test/particle_tunes_probe.jl:200` releases
all barriers and proves a subsequent execution succeeds; the clear APIs share
the entry guard. Both clears were also attempted while the admitted execution
was paused before the manager running flag was set: both refused, the atomic
guard remained held after each refusal, and both succeeded after completion.
This distinguishes the entry guard from a later manager-flag check.

**U3-2, immutable coordinate-wrapper ownership.** The concurrency fixture first
used an immutable wrapper and failed owner matching instead of exercising the
race. That prompted measurement with real `SubArray` coordinates. A task
retaining the same `Phase6DRep` failed continuation after `GC.gc()` for both
particle tunes and reset, because a WeakRef targeted an ephemeral wrapper box.
The aperture-only sibling and StrongStrong's shared binding both lost their
owner, replaced the record and reset counts `[1] -> [0]`; TrackingTask emitted
an unattributed-loss warning. The shared `_coordinate_storage_owner` helper
now keeps weak references for mutable arrays and retains immutable wrappers
with a small `.value` holder. This deliberately keeps their parent storage
alive until clear/replacement. The permanent nine-feature test group includes
real views, GC continuation, both loss callers and foreign-storage refusal.
Corrected immutable-view block passed all 16 assertions; the existing reset
reentrancy/previous-trial preservation block passed all 40 assertions.

Negative controls also deliberately swap assigned labels, ignore an overridden
plane, use the wrong endpoint optics and redraw labels on every turn. Each is
rejected by the corresponding independent expected coordinates/labels.
The histogram boundary control selects `u=prevfloat(1)` with a subsequent
interior fraction of 1/2 for masses `[1,4,1,0]`; the current CDF normalization
correctly selects the third bin and returns 2.5. This was a checked hypothesis,
not a confirmed histogram defect.

## Corrections to this unit's own analysis and fixtures

1. An early response error bound scaled by a nearly cancelled whole output
   column. At Float32, zero spread with kicks, turn 11, particle 1, `py`, the
   reference was `-4.767981938574353e-7` and actual `-4.7597769f-7`; absolute
   error `8.205081474857141e-10` exceeded that incorrectly chosen scale's bound
   `8.002899371996747e-11` (ratio `10.252636067832936`). The forward carrier was
   `0.0022659827540107563`, giving `3.803376814898425e-7` with the unchanged
   `128 eps(T) turns` multiplier. The raw output-scaled diagnostic remains in
   the harness. Independent phase/action/centroid/covariance evidence passed
   before and after. No production numerical change was made for this case.
2. The first MPI presence negative-control expectation demanded a timeout plus
   three successful peers. Real mismatched collectives instead caused peer
   mutations, bogus shard counts and an MPI abort. The acceptance criterion
   was corrected to require the actual failure of coherent refusal, rather
   than a particular process hang. The observed rank receipts were preserved. Running the portable archived
   harness reproduced the same fatal `MPI_Allgather` message truncation before
   any rank returned from `execute!`; all four entry receipts were present.
   Thus its revised demand for a peer post-return mutation receipt was also
   too specific. The definitive signal in that run is the fatal collective
   signature, not completion timing. The fixed production launcher separately
   completed all one/two/four-rank checks. The archived-control combined runner
   exited nonzero at its own overly narrow presence assertion; it is not
   reported as an all-green run.
3. The first concurrency wrapper was immutable. Both calls refused owner
   matching (arrived=2, accepted=0, refused=2), so that run was not a valid race
   reproduction. A mutable wrapper isolated the intended concurrency race;
   the independent real-view probe then established the separate owner defect.
4. A tentative histogram trailing-zero hypothesis was checked after noticing
   cumulative rounding. The constructor already normalizes its CDF, so this
   lead is closed as sound behavior. Constant `prevfloat(1)` for both RNG
   draws rounds an interpolation endpoint to 3.0; separating selection and
   interior draws avoids mistaking endpoint rounding for selection of a
   zero-mass bin.

5. The first new view regression incorrectly expected reset summary totals to
   accumulate across execution calls. The API counts only the latest admitted
   window, so its correct value was one, not two. That runner passed all 13
   other view checks. The corrected block pins one completed trial per window
   plus unchanged reference epoch and capture turn, and passes 16 checks. This
   was a fixture expectation correction, not another production fix.

## Final targeted checks, performance and limits

The final focused feature checks passed 684 assertions in nine testsets:
113 dense/backend/receipt checks, 173 source/entrance checks, 51 distribution
checks, 167 lifecycle checks, 143 physics checks, five warning checks, five
admitted-failure loss checks, 11 atomic-admission/clear checks and 16 immutable-view
checks. The adjacent existing reset reentrancy block passed 40 assertions.
The first eight blocks ran together under CUDA-active execution (the atomic
block then had six checks); the corrected view block and reset sibling ran in
the next focused invocation. The expanded 11-check atomic block, including
pre-admission clear refusal, passed in a final invocation before its archived
MPI negative-control launcher reported the fixture criterion issue described above.

This unit did not run the final full package gate; the campaign lead owns that
receipt. It did not benchmark execution time. It added an ordinary
heterogeneous-tuple allocation control for the new feature predicate and
measured actual workers/launches as effectiveness checks; before/after
allocation and time measurements are produced by the lead
[`allocation probe`](../audit_particle_tunes_2026_10_30_allocation_probe.jl). The existing two
expected-broken misalignment convention checks were not modified.

The implementation intentionally does not offer Metropolis-Hastings fitting
or establish mixing/convergence of arbitrary user distributions. It accepts
prepared joint samplers/histograms and freezes their labels. It does not
validate a coordinate-dependent callback's map as a nonlinear symplectic map;
the contract applies to the linear map with labels held fixed. Generic
checkpoint serialization, arbitrary in-place particle reordering, transformed
nested bodies, active StrongStrong bindings, non-Float32/64 active runtimes and
common-matrix/Twiss extraction from heterogeneous tunes remain out of scope.
