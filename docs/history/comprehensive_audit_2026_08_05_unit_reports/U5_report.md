## Leads

### U5-1 — pic_cpu.jl:1317-1366 — PIC coordinates are NOT thread-count invariant above `_PIC_PARALLEL_DEPOSIT_MIN`, and the permanent pin cannot see it — MEDIUM
Invariant violated: test/runtests.jl:3037 "CPU solver stack is thread-count invariant … COORDINATES must be bit-identical (kicks are chunk-local, so no cross-worker reduction touches them)". The parenthetical is false for the PIC path: `_pic_deposit_threaded!` / `_pic_deposit_drifted_threaded!` reduce per-chunk charge grids in chunk order (`charge .+= local_grid`, pic_cpu.jl:1325-1327/1342-1344/1362-1364), a cross-worker float reduction that feeds phi → E → every kick. The pin uses 1500 particles / 3 slices = 500 per slice (test/runtests.jl:3071), below `_PIC_PARALLEL_DEPOSIT_MIN = 4096` (interface.jl:551), so the threaded deposit never executes under the pin — the "pic" and "gpic" rows test the serial deposit only.
Measured (probe1, 15000 particles / 3 slices = 5000/slice, grid 16×16, same config as the pin otherwise): beam-1 coordinates differ in 74,882 of 90,000 values at 1-vs-4 workers (max |Δ| = 2.52e-15), 74,918 at 1-vs-8, and 74,746 at 4-vs-8 — unlike the spectral fold, nchunks ≥ 2 are not even identical to each other. PIC luminosity differs by 154 ulps (1-vs-4), 53 ulps (1-vs-8), 101 ulps (4-vs-8) against the pin's exact `==` assertion for the pic label.
Repro: `scratchpad/U5/probe1_thread_invariance.jl`.

### U5-2 — slicing.jl:649-681 — `_slice_transverse_moments` thread-count dependent above `_STRONG_STRONG_PARALLEL_MOMENT_MIN`; same pin gap — MEDIUM
The threaded branch reduces `local_sums` in chunk order (slicing.jl:671-680); the serial branch accumulates in particle order. Above n = 4096 the results differ across worker counts: measured (probe1, n = 8192) `mx` differs by 53,248 ulps (2.07e-8 vs 2.07e-8, Δ ≈ 1.8e-19), `mpx` by 131,072 ulps (1-vs-8), `sx` by 24 ulps, every moment field differing at 1-vs-4, 1-vs-8 and 4-vs-8. These moments are the soft-Gaussian source representation (gaussian.jl:27-30), so GaussianPoissonSolver kicks — and coordinates — inherit worker-count dependence above the threshold. The pin's 500-per-slice beams never reach the threshold.
Repro: `scratchpad/U5/probe1_thread_invariance.jl`.

### U5-3 — pic_cpu.jl:820-888, 188-232 — `interaction_grid = :node` accepts and bit-identically ignores `slice_interpolation = :quadratic` — MEDIUM
`_pic_interaction_node!` has no quadratic branch (always the two-node zL/zR blend, lines 853-876) and `_pic_collide!` routes every node-mode pair there (line 79-94) without consulting `_pic_quadratic_slice`. `_validate_pic_solver` validates the two options separately and never rejects the combination — while the very same function rejects `grid_extent ≠ :extrema` for `:node` with a message about options being "silently ignored" (lines 216-230), and `_require_linear_slice_interpolation`'s docstring (line 376) states "A non-default public configuration value must never be silently ignored; see AGENTS.md".
Measured (probe3, 2000 particles, 3 slices): `:node`+`:quadratic` vs `:node`+`:linear` → 0 of 12,000 coordinate values differ, luminosity Δ = 0.0. Control `:slice_pair`+`:quadratic` vs `:linear` → 10,000 of 12,000 differ, luminosity Δ = 1.3e11.
Repro: `scratchpad/U5/probe3_node_quadratic.jl`.

### U5-4 — pic_cpu.jl:56-62, 751 — `green_cache = :slice_pair` silently does nothing under `interaction_grid = :node` — LOW
Node mode builds each node's Green FFT fresh via `_pic_green_fft` (line 751) inside a per-collide `node_cache` (line 56, rebuilt every turn); `_pic_slice_pair_green!` is never called, so the configured cache never stores or serves an entry and the diagnostics report prints all-zero stats. Measured (probe3): `:node` with `:none` vs `:slice_pair` → 0 differing values; control under `:slice_pair` grids: `:none` vs `:slice_pair` changes 5,000 of 6,000 beam-1 values (the cache legitimately alters meshes via the 1.25 growth), proving bit-identity under `:node` means "ignored", not "transparent". Performance/diagnostics option, hence LOW, but the same accepted-and-dropped class the file rejects loudly for `grid_extent`.
Repro: `scratchpad/U5/probe3_node_quadratic.jl`.

### U5-5 — pic_cpu.jl:571-586 vs 1241-1244 — under `grid_extent = :sigma`, SOURCE-side charge dropped by the deposit is never counted; "Never silent" is silent — MEDIUM-LOW
`workspace.dropped` counts only field particles against `field_grid` (lines 582-585). The source deposit (`_pic_deposit_drifted!` onto `source_grid`, whose extent is the same sigma estimator, lines 510-513) drops out-of-box source particles through the zero-weight branch with no counter, no warning. The struct comment (interface.jl:576-579) says "Never silent", and `_pic_report_dropped`'s warning text (pic_cpu.jl:148-150) claims to cover "charge … missing from the field" — which is exactly the uncounted half.
Measured (probe2b, 4001 source particles incl. one at 30 sigma, `grid_extent=:sigma`, k=2, field distribution fully inside its own box): deposited charge = 3999.99999999999 of 4001 (1.0 particle-charge missing), `workspace.dropped == 0`.
Repro: `scratchpad/U5/probe2_cic_edge_and_dropped.jl`.

### U5-6 — pic_cpu.jl:582-585, 938-945 — dropped counter double-counts a particle outside the mesh in both axes — LOW
The count is `_pic_count_outside(x) + _pic_count_outside(y)`; a corner escapee increments it by 2, though the docstring (line 129) and warning report it as a count of particles. Measured (probe2c): 1 field particle outside in both x and y → `workspace.dropped == 2`.
Repro: `scratchpad/U5/probe2_cic_edge_and_dropped.jl`.

### U5-7 — pic_cpu.jl:1421-1428 — `_pic_cic_weights` at u exactly n-1 (in-range by its own guard) deposits the full charge one cell inward — LOW
`base = clamp(floor(Int,u)+1, 1, n-1)` engages the clamp at u = n-1, but `f = u - floor(u) = 0` is computed from `floor(u)`, not from the clamped base, giving weights (1.0, 0.0) on nodes u = n-2, n-1 → all charge at u = n-2. Measured (probe2a): `_pic_cic_weights(4.0, 5) = (4, (1.0, 0.0))`; single-particle deposit at grid node (4,4) lands entirely in cell (4,4) → charge center of mass u = 3.0 vs particle at u = 4.0 (interior control at u=2 → CoM 2.0, correct). Same weights are used by `_pic_interpolate_kick`, so a field particle at the exact mesh top edge reads the field one cell inward. The CIC docstring documents drop-vs-clamp for out-of-range but implies in-range is correct. CUDA `_cuda_pic_cic_weights` (pic_cuda.jl:4282-4290) is bit-identically the same, so parity cannot see it (the "reference error invisible to parity" class). Reachability: measure-zero for continuous data (:extrema margins keep u ∈ [~1.5, n-2.5]; luminosity mesh u_max = n-1.05), exact-hit only for quantized/degenerate coordinates.
Repro: `scratchpad/U5/probe2_cic_edge_and_dropped.jl`.

### U5-8 — pic_cpu.jl:1895-1899 — luminosity overlap sum excludes deposit row nx+1 / col ny+1; with TSC that charge exists — LOW
`_pic_deposit!` fills (nx+1)×(ny+1) node arrays but the overlap sum runs `1:nx, 1:ny`. CIC provably never reaches the excluded row/col (probe: excluded charge 0.0). With `luminosity_deposit_method` resolving to `:TSC` (the default whenever `deposit_method = :TSC`, interface.jl:1303-1304), the topmost particles' third stencil cell is row nx+1/col ny+1: measured (probe5, 200 uniform particles, grid 16) 0.513 of 200 particle-charges (0.26%) deposited into the excluded row/col, relative luminosity deficit 8.0e-5. The `_pic_tsc_weights` docstring (lines 1448-1454) documents the deposit displacement and the 0.05-cell margin decision but not this sum exclusion. CUDA's overlap kernels sum the same `nx*ny` range (pic_cuda.jl:4381-4386), so this too is parity-invisible; it is a shared-convention accuracy note rather than a divergence.
Repro: `scratchpad/U5/probe5_lum_tsc_exclusion.jl`.

## Observations (not probed, flagged for the auditor)

- `_pic_tsc_weights` (pic_cpu.jl:1456-1473) uses untyped Float64 literals (0.125, 0.75…), so Float32 inputs produce Float64 weights, while `_cuda_pic_tsc_weights` types them `typeof(u)` and derives w3 as `1 - w1 - w2`; Float32 TSC runs will differ CPU-vs-CUDA in last ulps (parity tolerance presumably absorbs it).
- `:lattice` Green table is Float64-only (`_PIC_LATTICE_GREEN_CACHE`, line 1575) and `_pic_lattice_rho_key` calls `Float64(rho)`; a Dual-valued rho should fail loudly there (MethodError) rather than silently zeroing d(table)/d(rho) — not verified with a probe.
- `_pic_deposit_threaded!` (workspace variant, line 1335) falls back to the allocating threaded path on a worker-count mismatch while `_pic_deposit_drifted_threaded!` (line 1352) falls back to serial — both correct, inconsistent choices; unreachable in practice because the workspace cache key includes `_cpu_worker_count()`.
