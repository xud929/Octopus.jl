# U1 — the consumers and the runtime variants of the optics parameters

Reading unit of [`../audit_linear_optics_2026_11_21.md`](../audit_linear_optics_2026_11_21.md).
Region: `src/elements/linear6d.jl` (the two-point constructors, `form1`/`form2`,
`_mR66(C, form)`, `_check_linear6d_block`), `src/elements/particle_tunes.jl`
(the second runtime variant of the kind), `src/elements/chromaticity_kick.jl`,
`src/elements/radiation.jl`, `src/elements/strong_beam.jl`,
`src/elements/linear_maps.jl`, `src/beam/Beam.jl`, `src/knowledge/LinearOptics.jl`.
Hypothesis: a parameter added to a spec kind has every reader of that kind's
parameters as a consumer, and a value-level "given" test cannot see an explicit
default. Inspected by the auditor directly (no sub-agent), 2026-11-21.

### LEAD U1-1 [Moderate, confidence high] src/elements/particle_tunes.jl:340-357, 378-386
Claim: `ParticleLinear6D`, the particle-tune runtime variant of `ElementSpec{:linear6d}`,
reads `beta1/2`, `alpha1/2`, `zeta1/2`, `eta1/2`, `R1/2` to build its entrance and
exit normalizers but never `form1`/`form2`, and builds the coupling block with the
form-1 `_mR66` for any form; it also reaches `sqrt` of a negative number for
`det C >= 1` instead of the named refusal the plain map gives.
Mechanism: `_particle_tune_normalizer(beta, alpha, zeta, eta, coupling, T)` calls
`_mR66(coupling)`, the one-argument form kept for compatibility, which is form 1;
`ParticleLinear6D(spec, method)` never calls `getparam(spec, :form1, 1)`.
Repro: `docs/history/audit_linear_optics_2026_11_21_U1_1_repro.jl` on the unfixed
tree prints, for `form1 = 2` with `R1 = (0.05, 0.01, -0.02, 0.03)`,
`|A - form1 expectation| = 0.00e+00, |A - form2 expectation| = 5.83e+00`: the
normalizer is form 1 whatever the form.
Root response: confirmed and fixed in the batch -- `_particle_tune_normalizer`
takes `form`, calls `_mR66(C, _linear6d_form(form, :form))` and
`_check_linear6d_block(C, :R)`; `ParticleLinear6D(spec, method)` reads
`form1` and `form2` with the same partner defaults as the plain map. Pinned in
the suite testset "LinearOptics: the shared optics object ..." (the normalizer
equals `_mR66(C, form) N` and differs from the other form; `det C >= 1` refused
by name through `compile_runtime`). The regression assertion fails on the
unfixed tree for the defect's reason (the repro's numbers).

### LEAD U1-2 [Minor, confidence high] src/beam/Beam.jl (the Gaussian path's `optics` flattening)
Claim: the first implementation detected a flat optics keyword beside `optics`
by comparing its VALUE to the default (`beta == (1, 1, 1)`, `mode === XY_MODEA`,
`all(iszero, coupling)`), so an explicit `beta = (1.0, 1.0, 1.0)` or
`mode = XY_MODEA` beside `optics` was not refused and the point's values won
silently: two sources of truth, the case D4 of the design note forbids.
Mechanism: `_initialize_beam`'s keywords defaulted to values, not to `nothing`,
so "given" and "default" were indistinguishable.
Repro: on the tree before the fix, `Beam(10, CPUThreadsBackend; optics=o,
sigma=..., beta=(1.0, 1.0, 1.0))` constructs a beam with `o`'s beta.
Root response: confirmed and fixed in the batch -- `beta`, `alpha`, `zeta`, `eta`,
`coupling` and `mode` default to `nothing` in `_initialize_beam`, the clash
check is by presence, the defaults are applied after it and before the bounded
forward (so the bounded path's neutral-value checks see the same values as
before). Pinned in the suite: three explicit default-valued keywords beside
`optics` refused; the flat beam and the object beam remain bit-identical.

### Clean regions, with the evidence that makes "clean" checkable
- `Linear6DSpec(o1, o2)` refuses every optics keyword and `matrix` by key
  presence (the `clash` list), passes `tracking_method`, `particle_tunes`,
  `rng_id`, placement and metadata through; typed and untyped forms store the
  same parameters (suite: `params` equality against the flat form).
- `_linear6d_matrix_from_optics` and `ParticleLinear6D` are the only two
  readers of the optics parameters in `src/` (grep for `:R1`, `:zeta1`,
  `:form1`); `Contracts.jl:3786` holds the effectiveness probe (optics form,
  nonzero `R1`/`R2`; `form1`/`form2` perturbed from absence through their
  alternatives and measured effective, deviations 2.7e-4 and 1.1e-3);
  `Contracts.jl:4342` special-cases `particle_tunes`/`rng_id` only.
- `ChromaticityKickSpec` and `LumpedRadSpec` resolve `optics` before any
  stream is claimed (`_resolve_optics_keywords` precedes `next_rng_id!` in
  `radiation.jl`); their kernels are untouched, so their CUDA twins are not in
  the blast radius; both refuse a form-2 point by name.
- `ThinStrongBeamSpec`: `optics` is consumed and never stored (like `beta`,
  `alpha`, `sigma`, `coupling` before it); the stored covariance equals the
  flat form's for the uncoupled, the coupled form-1 and the form-2 points
  (suite); a point with dispersion is refused by name.
- `XYCoupling`: the `XY_UNDEF` refusal sits in the spec constructor and in the
  runtime inner constructor, so `Beam`'s direct `XYCoupling(...)` construction
  is covered too (and refused earlier, before the draw, by `_check_undef_coefficients`
  in `_initialize_beam`); `_inverse(::XYCoupling)` and the rounding class keep
  their identity branches for the zero-coefficient case. No example or
  validation script constructs `XY_UNDEF` or a nonzero `R1` (grep of
  `examples/`, `validation/`).
- Baseline fingerprints: 14 of 14 flat-path hashes identical before and after
  the batch (CPU and CUDA), the evidence that no flat path moved.
